[A4] — Found via the audit hash-chain test, but a systemic issue, not an audit-only one: SQLite's driver silently returns a NAIVE datetime from a `DateTime(timezone=True)` column on read, even though a tz-aware value was written. `/audit/verify` was failing on an UN-tampered chain because the hash was computed once at append time (tz-aware `at`) and again at verify time on a freshly re-read row (naive `at`, no "+00:00" in the isoformat string) — two different canonical strings, two different hashes, no tampering involved. Fixed at the root with a `UTCDateTime` TypeDecorator in shared/infrastructure/db.py (re-attaches UTC tzinfo on read, exported via the shared facade) and migrated every existing DateTime column (intake's five tables, audit's one) to it, not just audit's. Any future module's timestamp column should use `shared.UTCDateTime`, never a bare `DateTime(timezone=True)`, or the same class of bug recurs silently.
[A4] — A second, related clock bug, inverse of A3's SIM_CLOCK_EPOCH one: `Login` originally computed the session cookie's expiry from the injected (simulated) `Clock`, which starts at SIM_CLOCK_EPOCH (1970) and had not been advanced in a fresh test app — so every login cookie was already "expired" in 1970 and httpx's cookie jar silently dropped it (login returned 200, but no session cookie ever reached the client; every subsequent `/auth/me` call then got 401 for what looked like no reason). Cookie/JWT expiry is a wall-clock, transport-level concern like LC-6's webhook timestamp window (DOC 2 §2.4), never the simulated timeline, so `Login.run` now calls `SystemClock().now()` directly for `expires_at` and no longer takes a `clock` parameter at all (nothing else in Login needed it). Same lesson as A3's SIM_CLOCK_EPOCH fix in the opposite direction: name, for every new timestamp, which clock (sim or wall) it should come from before wiring it, rather than defaulting to whichever Clock instance is already in scope.
